# 튜토리얼 시작 딜레이 제거 · 전환 렉 계측 설계

- 작성일: 2026-07-26
- 대상: `MainCoachmark`(코치마크 오버레이)와 이를 띄우는 메인·통계·프로필 화면
- 상태: 설계 승인됨, 구현 계획 대기

## 배경

튜토리얼에 두 가지 증상이 보고됐다.

1. **시작 딜레이** — 화면에 들어온 뒤 한동안 아무것도 없다가 말풍선이 뜬다.
2. **단계 전환 렉** — "다음"을 눌러 넘어갈 때 버벅인다.

이 중 2번은 이번 세션에서 이미 네 차례 수정했다. SVG 마스크를 거대 테두리 뷰로 교체하고, 링 맥동(`RING_PULSE`)과 스포트라이트 이동(`SPOTLIGHT_GLIDE`)을 끄고, 움직이는 뷰의 그림자·글로우를 제거하고, 튜토리얼 중 지구본 WebView를 정지시켰다. 그럼에도 증상이 남았다면 **원인이 지금까지 지목한 곳이 아니다.**

네 번의 수정은 모두 "이것이 원인일 것이다"라는 추정에서 출발했고, 뒤의 두 번은 빗나갔다. 그래서 이번에는 추정으로 더 깎지 않는다. **계측을 먼저 넣고, 숫자를 보고 고친다.**

한편 증상 1은 원인이 이미 확정돼 있다. 계측이 필요 없다.

## 원인 분석

### 시작 딜레이 (확정)

세 화면 모두 튜토리얼 시작이 같은 형태다.

```
setTimeout(450ms) → 요소 측정 → 단계 구성 → setCoachVisible(true) → 등장 페이드(260ms)
```

- `src/screens/MainScreen.tsx:398` — `setTimeout(..., 450)`, 이후 4개 요소 측정
- `src/screens/StatsScreen.tsx:459` — 같은 구조, 1개 측정
- `src/screens/ProfileScreen.tsx:1391` — 같은 구조, 3개 측정
- `src/components/MainCoachmark.tsx:164` — 등장 페이드 260ms

**약 750ms 동안 아무것도 안 보이는 것이 현재의 정상 동작이다.** 450ms는 "화면 레이아웃이 자리 잡을 때까지 기다리자"는 목적으로 넣은 값이지, 측정해서 정한 값이 아니다. 실제 필요한 대기는 **화면 전환 애니메이션이 끝날 때까지**이며, 그 시점은 기기와 상황에 따라 다르다. 빠른 기기에서는 450ms 중 대부분이 순수한 낭비다.

### 전환 렉 (미확정)

현재 개발 빌드에서만 확인됐다. Metro dev 모드는 리액트 커밋이 릴리스보다 5~10배 느려서, 개발 빌드에서 보이는 렉은 실사용자가 겪는 것보다 과장돼 있다. 릴리스 기준 실측이 없는 상태다.

## 설계

### 1. 계측 — `src/utils/perfTrace.ts` (신규)

그룹 단위로 구간 시간을 찍는 최소 유틸. 기본적으로 개발 빌드에서만 동작하며, 릴리스에서는 모든 함수가 즉시 반환한다. 호출부를 지울 필요가 없다.

```ts
traceStart('coach')            // 그룹 시작(기준점 기록)
traceStep('coach', 'measured') // [perf] coach · measured +312ms (총 312ms)
traceEnd('coach', 'visible')   // 그룹 종료 + 총합 출력 후 기준점 삭제
```

**릴리스 측정 스위치**: 모듈 상단에 `const TRACE_ENABLED = __DEV__;`를 두고, 한 줄을 `true`로 바꾸면 릴리스 빌드에서도 한 번 측정할 수 있게 한다. dev/release 숫자를 같은 잣대로 비교하려면 이 경로가 필요하다. 기본값은 `__DEV__`이며, 커밋되는 값도 `__DEV__`다.

**호출 지점 6개**

| 지점 | 위치 | 알 수 있는 것 |
|---|---|---|
| `trigger` | 세 화면의 튜토리얼 시작 시점 | 기준점 |
| `waited` | 준비 대기가 끝난 직후 | 대기가 실제로 얼마나 잡아먹는지 |
| `measured` | 요소 측정 완료 | 측정 자체의 비용, 재시도 횟수 |
| `visible` | `setCoachVisible(true)` 커밋 후 | **등장까지 총 시간** |
| `step:committed` | 단계 변경 후 첫 렌더 커밋 완료 | **전환의 JS·커밋 비용** |
| `step:settled` | 크로스페이드 종료 | 전환 체감 시간 |

그룹은 둘로 나눈다. `coach`(trigger → waited → measured → visible)는 화면이 관리하고, `coach:step`(step 시작 → committed → settled)은 `MainCoachmark`가 단계마다 새로 시작한다.

`step:committed`는 `MainCoachmark` 안에서 `idx`를 의존성으로 갖는 `useEffect`에서 찍는다. 이펙트는 커밋 완료 후 실행되므로 커밋 종료 시점의 근사치로 유효하다.

### 2. 시작 딜레이 수정 — `src/utils/coachStart.ts` (신규)

고정 대기(`setTimeout(450)`)를 **준비 신호 기반**으로 교체한다.

1. **`InteractionManager.runAfterInteractions()`** — 화면 전환 애니메이션이 끝난 뒤로 미룬다. 450ms를 넣은 진짜 이유가 "전환 중에 측정하면 이동 중인 좌표가 잡힘"이므로, 이것이 정확한 대체물이다.
2. **측정 재시도** — `measureInWindow` 결과가 유효하지 않으면 다음 프레임에 다시 시도한다. 유효해지는 즉시 진행하고, 상한은 20프레임(약 330ms)이다.

빠른 기기에서는 1~2프레임(약 30ms)이면 끝나고, 느린 기기에서는 필요한 만큼만 기다린다. 지금은 빠르든 느리든 무조건 450ms다.

**유효한 rect의 정의** — 다음을 모두 만족해야 한다.

- `x`, `y`, `width`, `height`가 모두 유한한 숫자 (`NaN`·`Infinity`·`-Infinity` 제외)
- `width > 0` 이고 `height > 0`
- 좌표의 부호는 따지지 않는다 — 스크롤로 화면 위로 밀린 요소는 정상적으로 음수 `y`를 갖는다

현재 세 화면의 측정 헬퍼는 `NaN`만 걸러내고 **폭·높이 0을 통과시킨다.** 레이아웃 전 요소가 0×0으로 측정되면 스포트라이트가 좌상단에 점으로 찍힌다. 재시도 조건에 폭·높이를 넣는 것이 이 문제도 함께 해결한다.

**공용화** — 세 화면이 측정 헬퍼를 각각 복붙하고 있다(`MainScreen.measure`, `StatsScreen.measure`, `ProfileScreen.measureRect` — 이름만 다르고 내용 동일). `coachStart.ts`로 합친다.

```ts
isValidRect(r): boolean                          // 순수 함수, 테스트 대상
measureWithRetry(ref, maxFrames?): Promise<CoachRect | null>
whenReadyToMeasure(): Promise<void>              // runAfterInteractions 래퍼
```

세 화면은 `setTimeout(450)` 대신 `await whenReadyToMeasure()` 후 `measureWithRetry`를 호출한다. 취소(화면 이탈) 처리는 지금처럼 각 화면의 `cancelled` 플래그로 유지한다 — cleanup에서 `cancelled = true`로 두고, 각 await 뒤에 확인한다.

**등장 페이드 260ms → 200ms**: 딜레이 체감의 일부이므로 이번 구현에 포함한다. 계측 결과가 다른 값을 가리키면 그때 재조정한다.

**측정 실패 시**: 상한까지 유효한 값을 얻지 못하면 `null`을 반환하고, 호출부는 지금처럼 상수 폴백(스냅 버튼)을 쓰거나 해당 단계의 스포트라이트를 생략하고 진행한다. **튜토리얼이 아예 뜨지 않는 경우는 없어야 한다.**

### 3. 전환 렉 — 숫자에 따른 판단 기준

계측 후 `step:committed`(전환 시작 → 커밋 완료)와 `step:settled`(→ 크로스페이드 종료)를 본다. **어떤 값이 나오면 무엇을 고칠지 미리 정해두는 것이 이 절의 목적이다.** 숫자를 보고 그때 원인을 새로 추정하면 지난 네 번과 같은 실패를 반복한다.

| 관측 | 해석 | 조치 |
|---|---|---|
| `committed`가 큼 (dev 기준 80ms 이상) | 리액트 커밋이 병목 | 말풍선을 `React.memo` 하위 컴포넌트로 분리, 딤 뷰 props 참조 안정화, 그라데이션 `colors` 배열 재생성 제거 |
| `committed`는 작은데(30ms 이하) 체감 렉 | JS가 아니라 네이티브·GPU | 거대 딤 뷰(화면의 수 배 크기 + 큰 `borderRadius`) 재래스터화가 유력 → 크기 축소 또는 4분할 사각형 + 모서리 조각으로 교체 |
| 둘 다 작은데 느리게 느껴짐 | 렉이 아니라 **연출 길이** | 크로스페이드가 아웃 130ms + 인 220ms로 직렬 350ms → 겹치거나 단축(예: 90 + 160) |
| dev 대비 release가 크게 작음 | dev 오버헤드가 주원인 | 여기서 멈춘다 — 실사용자에게는 문제없음 |

**이 절의 조치는 이번 구현에 포함하지 않는다.** 판단 규칙으로만 남기고, 계측 결과를 본 뒤 별도로 진행한다.

### 4. 검증

**성공 기준** (개발 빌드 기준, 잠정 — 계측 후 현실적인 값으로 확정)

- **시작**: `trigger → visible` **250ms 이하** (현재 약 750ms)
- **전환**: `step:committed` **50ms 이하**
- 두 값 모두 수정 전/후를 같은 기기·같은 방식으로 비교해 기록한다

**자동 검증** — `isValidRect`는 부수효과가 없는 순수 함수이므로 `src/utils/coachStart.verify.ts`에 테스트를 붙인다. 프로젝트의 기존 방식(`handleSearch.verify.ts` 등)을 따라 jest 없이 `npx tsx`로 실행한다.

- `NaN`, `Infinity`, `-Infinity` 포함 시 무효
- `width` 또는 `height`가 0이면 무효
- 음수 `y`(스크롤로 화면 위로 밀린 요소)는 **유효**
- `null`·`undefined`·필드 누락 안전

타이밍과 애니메이션은 기기에서만 확인 가능하므로 수동 점검으로 둔다.

**회귀 점검** — 성능 수정이 기능을 깨지 않았는지 수동 확인한다.

| 항목 | 확인 내용 |
|---|---|
| 3개 화면 | 메인·통계·프로필 튜토리얼이 각각 정상 등장 |
| 스포트라이트 위치 | 특히 스냅·FAB(상수 폴백 경로가 있는 곳)이 제자리인지 |
| 측정 실패 폴백 | 요소를 못 찾아도 튜토리얼이 뜨는지 |
| 1회 게이트 | 계정당 탭별 1회 노출·설정에서 다시보기가 그대로인지 |
| 터치 차단 | 튜토리얼 중 탭 바·스냅·FAB가 안 눌리는지 |
| 타입 체크 | `npx tsc --noEmit` 통과 |

**중단 조건** — 계측 결과 dev/release 차이가 지배적이고 release가 기준을 만족하면, 전환 렉은 **더 손대지 않고 종료한다.** 이미 네 라운드를 쓴 사안이라 "release에서 괜찮으면 끝"을 명시적 종료 조건으로 둔다.

## 실측 결과 (2026-07-26, 개발 빌드)

계측을 넣고 실제로 재보니 판단 기준표의 **두 번째 행**이었다.

| 구간 | 실측 | 해석 |
|---|---|---|
| `trigger → visible` | 124~256ms (기존 약 750ms) | 시작 딜레이 해결 |
| `faded-out` | 141ms (설계 130ms) | 정상 — 여기까지 JS 스레드 멀쩡 |
| `committed` | 35~42ms (기준 50ms) | **리액트 커밋은 범인이 아니었다** |
| `geom-done` | 58ms | 딤 뷰 좌표 갱신 비용 |
| `js-free` | +1ms | JS 스레드는 완전히 자유로움 |
| `settled` | **411~1106ms** (설계 220ms) | **UI(네이티브) 스레드가 막혀 있었다** |

네이티브 드라이버로 도는 220ms 페이드인이 1,100ms 걸리는데 JS는 놀고 있었다 —
UI 스레드 기아 상태다. 원인은 딤 뷰였다. 한 변이 3,000dp를 넘고(화면 넓이의 약 30배)
테두리 반지름이 1,500dp대인 라운드 사각형 하나로 딤을 그렸는데, 단계가 바뀔 때마다
그 거대한 경로를 다시 테셀레이션하느라 UI 스레드가 수백 ms 멈췄다.

**조치**: 딤을 구멍의 사각 경계에 정확히 맞물리는 민 사각형 네 장 + 귀퉁이 네 곳의
클리핑 창으로 교체했다. 가장 큰 뷰가 구멍 반지름의 3.2배(지구본 단계 약 550dp)로
묶여, 구멍이 화면 어디에 있든 비용이 일정하다.

중간에 낸 실수 하나를 기록해 둔다. 처음에는 사각형 네 장 + **구멍 둘레 테두리 한 장**으로
만들었는데, 뷰 테두리는 바깥쪽도 라운드라 사각 경계의 네 귀퉁이가 딤 없이 남았다.
화면에 지름 520dp짜리 원이 비쳐 보였다. 이 부분은 한 장으로 채울 수 없고,
귀퉁이마다 클리핑 창이 필요하다.
