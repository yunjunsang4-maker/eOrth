# 여행 DNA 설문 설계

- 작성일: 2026-08-05
- 상태: 설계 확정 / 구현 전
- 영향: `mate_suggestions` 점수 체계 재편(6축 → 4축 + 설문축), 신규 화면·테이블

---

## 1. 배경

여행 DNA는 이미 있다. 다만 **기록에서 서버가 계산하는** 방식이고, 축이 여섯이다
(`mate_suggestions`, 총점 100 = 매칭률 %).

| 기존 축 | 배점 | 근거 |
|---|---|---|
| 장소 | 40 | 나라(희소성 가중) + 도시 겹침 |
| 시의성 | 15 | 최근 1년 내 겹친 나라 |
| 계절 | 10 | 같은 나라·같은 계절 |
| 관심사 | 15 | 기록 키워드 겹침 |
| 성향 | 10 | 별점·예산·항공편 평균 |
| 공통 메이트 | 10 | 함께 아는 사람 |

**문제는 여섯 축 전부 기록이 쌓여야 작동한다는 것이다.** 후보를 좁히는 1단계부터
`나라 겹침 or 공통 메이트`라, 기록이 없는 신규 사용자는 추천 후보에 아예 들어가지 못한다.

동시에 계절·관심사·성향 세 축은 **기록에서 억지로 짜낸 약한 신호**다. 키워드는 안 달면 0,
별점·예산은 대충 적히고, 계절은 취향이 아니라 그저 여행 시기다.

→ 이 셋을 걷어내고 **직접 묻는다.** 정확도가 오르고, 기록 없이도 매칭이 성립한다.

### 문항을 고칠 때의 규칙

- **A/B는 좋고 나쁨이 아니라 반대 방향이다.** 한쪽이 명백히 나쁘게 읽히면 응답이 쏠려
  그 문항의 변별력이 0이 된다.
- **축마다 문항 수가 달라도 된다.** 점수는 그 축의 가중치 합으로 정규화한다(§5).
- 문항 id는 **재사용하지 않는다.** 삭제한 번호는 비워 두고 새 문항은 다음 번호를 받는다 —
  `answers` jsonb가 id로 저장되므로, 번호를 돌려쓰면 옛 응답이 다른 문항의 답으로 해석된다.

## 5. 채점

각 문항은 선택한 방향으로 가중치만큼 이동한다. 축 점수는 **답한 문항의 가중치**로 정규화한 뒤,
**응답량에 비례해 중립으로 수축**시킨다.

```
raw  = 100 × Σ(B를 고른 문항의 w) / Σ(답한 문항의 w)
conf = Σ(답한 문항의 w) / Σ(그 축 모든 문항의 w)      -- 0~1
score = round( 50 + (raw - 50) × conf )
```

`0` = A 방향 극단, `100` = B 방향 극단, `50` = 중립.
문항을 늘리거나 줄여도 다른 축과의 균형이 깨지지 않는다.

**수축이 반드시 필요한 이유**: 온보딩 축약판은 축당 1문항이다. 수축이 없으면
그 한 문항으로 점수가 **0 아니면 100**이 되어, 7문항만 답한 사람이 모든 축에서 극단으로 찍힌다.
그 상태로 매칭에 들어가면 "확신에 찬 오답"이 된다.

```
축약판(5문항 중 w=2짜리 1개만 답함) → conf = 2/7 = 0.29
  B를 골랐어도 raw 100 → score 64      (극단이 아니라 '약한 B 성향')
전체 응답 → conf = 1 → score = raw     (수축 없음)
```

응답이 쌓일수록 점수가 자연스럽게 극단으로 자라난다. 별도 보정 로직이 필요 없다.

**무응답 축**: `conf = 0` → `score = 50`(중립).

## 6. 유형 라벨

7축이면 조합이 128가지라 프로토타입을 미리 쓰는 방식은 커버가 성기다.
대신 **가장 강한 축이 명사, 두 번째 축이 수식어**가 되는 조합식으로 만든다.

강도는 중립(50)에서의 거리 `|score - 50|`로 잰다.

| 축 | 명사 (A / B) | 수식어 (A / B) |
|---|---|---|
| ① 계획 | 계획가 / 방랑자 | 계획적인 / 즉흥적인 |
| ② 활동 | 휴양객 / 탐험가 | 느긋한 / 부지런한 |
| ③ 환경 | 도시인 / 자연인 | 도시를 걷는 / 자연을 찾는 |
| ④ 씀씀이 | 실속파 / 플렉서 | 알뜰한 / 아낌없는 |
| ⑤ 목적 | 미식가 / 관람객 | 맛을 좇는 / 눈으로 담는 |
| ⑥ 분위기 | 축제파 / 은둔파 | 북적임을 즐기는 / 조용함을 아끼는 |
| ⑦ 동행 | 혼행자 / 동행자 | 혼자가 편한 / 함께가 좋은 |

방향은 점수가 50보다 작으면 A쪽, 크면 B쪽이다.

```
⑤ 목적이 미식 쪽으로 가장 강하고, ② 활동량이 활동 쪽으로 그다음이면
   → "부지런한 미식가"

③ 환경이 자연 쪽으로 가장 강하고, ⑥ 분위기가 한적 쪽으로 그다음이면
   → "조용함을 아끼는 자연인"

⑦ 동행이 혼자 쪽으로 가장 강하고, ① 계획성이 즉흥 쪽으로 그다음이면
   → "즉흥적인 혼행자"
```

작성할 문구가 28개뿐이라 품질을 사람이 통제할 수 있고, 축을 늘려도 규칙은 그대로다.

**폴백**: 모든 축이 중립에서 15 이내면 `아직 색이 옅은 여행자`.
동점이면 축 번호가 빠른 쪽이 명사를 갖는다(결정론적이어야 같은 응답에 같은 라벨이 나온다).

## 7. 매칭 — 35점

7축 균등 5점. 축별로 두 사람의 점수 차를 유사도로 바꾼다.

```
d = |내 점수 - 상대 점수|          (0~100)
s = max(0, 1 - d / 50)
축 점수 = 5 × s                    합계 최대 35
```

**`/100`이 아니라 `/50`인 이유**: 무작위 두 사람의 축별 평균 차이가 약 33이다.
`/100`을 쓰면 아무나 0.67을 받아 변별력이 사라진다.

### 재편된 총점

| 축 | 배점 | 출처 |
|---|---|---|
| 장소(나라+도시) | 40 | 기록 |
| 시의성 | 15 | 기록 |
| 공통 메이트 | 10 | 기록 |
| **설문 성향** | **35** | 설문 |

### 정규화 — 한쪽이 설문을 안 했을 때

설문 축을 0으로 두면 설문 안 한 사람이 추천에서 부당하게 밀린다.

> **둘 다 유효 응답이 있을 때만 100점 만점. 아니면 기록 축 65점 만점을 100으로 환산한다.**

**유효 응답 = 모든 축에 답이 1개 이상.** 즉 온보딩 축약판(7문항)만 마쳐도 유효다 —
수축(§5) 덕분에 응답이 적으면 점수가 중립에 머물러 매칭에 과한 영향을 주지 않으므로,
문턱을 낮게 잡아도 안전하다.

기존 사용자 경험이 그대로 유지된다.

**반대로 기록이 없는 신규는 정규화하지 않는다.** 겹친 나라가 하나도 없는데 100%로 뜨면
거짓말이다. 35%는 정직한 숫자로 그대로 보여준다.

## 8. 추천 후보에 신규를 넣기

`mate_suggestions`의 1단계는 후보를 **나라 겹침 또는 공통 메이트**로만 좁힌다.
즉 기록 없는 신규는 설문을 마쳐도 **후보에 안 들어와 추천이 0이다.** 설문의 값어치가 여기서 죽는다.

→ 후보 선정에 세 번째 경로를 추가한다: **설문 완료자 중 `updated_at` 최근순 표본**(약 100명).
전역 근접 계산은 비싸므로 표본을 섞고 점수로 정렬한다. `travel_dna(updated_at desc)` 인덱스가 근거다.

### 캐시 무효화

`mate_suggestions_cache`(TTL 6시간)의 무효화 트리거는 현재 `posts` INSERT/DELETE에만 걸려 있다.
**설문을 마쳐도 6시간 동안 추천이 안 바뀐다.**
→ `travel_dna` INSERT/UPDATE에도 같은 트리거를 단다.

## 9. 데이터 모델

```sql
create table if not exists public.travel_dna (
  user_id    uuid primary key references public.profiles(id) on delete cascade,
  answers    jsonb not null,        -- {"1":"A","2":"B",...} 원본. 문항 추가 시 소급 재계산용
  scores     smallint[] not null,   -- 7축, 각 0~100
  type_key   text,                  -- 파생 라벨 키(표시용 캐시)
  answered   smallint not null,     -- 답한 문항 수
  updated_at timestamptz not null default now()
);
create index if not exists idx_travel_dna_updated on public.travel_dna (updated_at desc);
```

`answers`를 저장하는 이유: 문항을 추가하거나 가중치를 조정했을 때 **재검사 없이 점수를 다시 계산**할 수 있다.

### RLS와 공개 범위

- `select` / `insert` / `update` — **본인 행만**
- 타인에게는 **`type_key`만** `public_profiles` 뷰로 노출. 축 점수는 열지 않는다
  - 매칭 계산은 `security definer` RPC 안에서 도니 점수를 공개할 이유가 없다
  - "혼자 ↔ 함께" 같은 축은 그대로 노출되면 불편할 수 있다

### 클라이언트

로컬은 **읽기 캐시**로만 둔다(오프라인에서도 내 유형은 보여야 한다).
서버가 진실이며, 제출은 온라인에서만. 오프라인 응답은 로컬에 쌓였다가 다음 접속에 올린다.

로그아웃 시 캐시를 지운다 — 계정 귀속 데이터라 남기면 다음 계정에 남의 유형이 보인다.

## 10. 진입점

| 위치 | 형태 |
|---|---|
| 온보딩 | **7문항 축약판**(축당 대표 1문항, 약 40초) + 크게 보이는 건너뛰기 |
| 메이트찾기 | 상단 배너 — 미완료면 "성향 알아보기", 부분 완료면 "이어서 답하기" |
| 프로필 | 결과 카드(유형 라벨 + 7축 막대) · 재검사 진입 |

**온보딩만 예외인 이유**: 36문항은 3분이다. 지금도 온보딩이
`기본정보 → 사진 스캔 → 사진 선택`으로 길어, 여기에 3분을 더하면 이탈 지점이 하나 더 생긴다.
7문항으로 임시 유형을 만들어 두고, 나머지 29문항은 메이트찾기·프로필에서 마저 받는다.

축약판 대표 문항: **1 · 6 · 11 · 16 · 21 · 26 · 31** (각 축의 가중치 2짜리 첫 문항).

## 11. 구버전 앱 호환 (배포 함정)

RPC 반환 컬럼에서 `season_score` · `interest_score` · `taste_score`를 **지우면 안 된다.**
서버를 먼저 올리는 동안 구버전 앱이 그 컬럼을 읽는다.

> 컬럼은 남기고 `0`을 반환한다. `survey_score`를 새로 추가한다.

배포 순서:

```
1. schema.sql 재실행 (travel_dna + RLS + RPC 재편 + 캐시 트리거 확장)
2. 앱 배포
```

1번만 먼저 나가도 구버전은 정상 동작한다(설문 축이 0이고 정규화가 65점 만점으로 돌아간다).
