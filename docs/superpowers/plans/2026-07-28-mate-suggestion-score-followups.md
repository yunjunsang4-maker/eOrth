브랜치 전체 리뷰가 찾아냈고, 근거를 남긴 뒤 범위 밖으로 분리했다.

## 먼저 해야 하는 것 — 서버 SQL 실행

`supabase/schema.sql`의 `mate_suggestions` 함수는 **아직 실행된 적이 없다.**
이 브랜치의 SQL은 로컬 Postgres가 없어 정독으로만 검증됐다.

**주의:** `drop function if exists`가 `create`보다 먼저 실행된다.
create가 실패하면 함수가 **사라진 상태로 남고**, 클라이언트는 실패를 삼켜(`catch → []`)
추천 섹션이 조용히 빈 채로 뜬다. 실패해도 구 함수가 살아남도록 감쌀 것:

```sql
begin;
-- schema.sql의 mate_suggestions 블록
commit;
```

실행 직후 확인:

```sql
select * from public.mate_suggestions(10);
```

## 규모가 커지면 물리는 것

### 성능 — 2단계 설계가 무효 상태

명세 §5는 "1단계에서 `posts.country_name` 인덱스로 후보를 싸게 추린다"고 했으나,
실제 `cand`는 `pub_country`(전체 공개 posts에 대한 JSONB lateral 전개 결과)를 대상으로 한다.
따라서 **`idx_posts_author_country`가 한 번도 쓰이지 않는다.**

- 매 호출 비용: O(전체 공개 posts) 스캔 + JSONB 전개 + 나라별 distinct 집계
- posts 1만 행 수준까지는 견딜 만하고, 10만 행부터 초 단위로 넘어간다
- 호출 빈도가 높다 — 메이트찾기 진입 + 소셜 피드 진입마다

해결은 인덱스가 아니라 구조다(`visibility <> 'private'`이 비선택적이라 어떤 인덱스도 안 듣는다):
`cand` 산출만 `public.posts`를 직접 조회해 인덱스를 살리고 `data->'countries'` 보강은 2단계에서만,
또는 `country_weight`를 머티리얼라이즈드 뷰로 분리.

`cand_weight_sum`(가중 자카드용)도 후보 200명의 전체 방문국을 훑으므로 같은 계열이다.
첫 실행 때 실행계획을 함께 볼 것.

### `cand`의 `limit 200`에 `order by`가 없다

어떤 200명이 남는지 미정의다. 상한이 물리는 순간 최고점 후보가 임의로 탈락하고,
같은 날 재조회하면 같은 결과라는 셔플의 결정성 약속도 후보 집합 단계에서 깨진다.

국내 기록 때문에 `대한민국`이 거의 모든 사용자의 `my_countries`에 들어가므로,
후보 집합이 사실상 전 사용자가 되어 **예상보다 빨리 도달한다.**

## 정확도

### `perCountryData`의 날짜·별점을 못 읽는다

`splitByCountry` 기록은 실제 `startDate`·`rating`이 `perCountryData[국가명]` 안에 있다
(`src/store/recordStore.tsx:65-72`). 이 브랜치가 `data->'countries'` 전개는 추가했으면서
`perCountryData`는 놓쳤다 — 다국가 여행을 살리자는 취지가 절반만 적용됐다.

### 별점 평균의 그리드가 다른 축과 어긋난다

`crating`/`my_rating`은 (게시물 × 나라) 격자에서 평균을 낸다.
3개국 여행 1건의 별점이 3번 반영된다. 다른 축(`ccity`·`ckw`·`cbudget`·`cflight`)은 (게시물) 격자다.
영향은 성향 3항목 중 1개 안(최대 약 3.3점).

### 셔플이 한국 시각 09시에 회전한다

`current_date`가 UTC 기준이라, "매일 바뀌되 같은 날 재조회하면 같은 결과"라는 주석과 어긋난다.
`(now() at time zone 'Asia/Seoul')::date`로 바꾸거나 주석을 정정할 것.

### 튜닝 상수 2개는 실측 없이 정한 값이다

- 가중 자카드의 스케일 보정 `×2` — "결합 집합의 절반을 공유하면 만점"
- 도시 축의 편재 국가 임계 `0.5` — 전체 사용자의 50% 이상이 방문한 나라는 제외

둘 다 실기기 분포를 보기 전에 정했다. 성향 축의 판정 기준(별점차 ≤1.0 / 예산 2배 이내 /
직항·경유 일치)도 느슨한 편이라 같이 볼 것.

**표본 20명 미만이면 희소성이 통째로 꺼진다**(명세 §1의 소표본 폴백).
그 전까지는 희소성 효과의 관측 자체가 불가능하다.

## 사용자 체감

### 근거 문구가 희소 나라 **이름**을 말하지 않는다

명세 §6의 1순위는 "아이슬란드·포르투갈을 함께 다녀왔어요"인데,
구현은 구 문구 "나와 겹치는 나라 2곳"을 그대로 쓴다.
`sample_countries`가 희소성 내림차순으로 정렬되도록 SQL을 고쳐놓고도 그 정보를 문구가 안 쓴다.

`friends.reasonCountry`를 신설하고 `sharedCountries`를 `ReasonInput`에 추가할 것.
조사 문제는 `reasonCity`와 같은 방식으로 회피형 문구를 쓸 것("둘 다 ~에").

### 영어 로케일

- 도시명·키워드가 한글 원문으로 나온다("You both visited 교토").
  `regionNameEn`(`recordStore.tsx:175`)이 이미 있으므로 RPC가 함께 뽑아 로케일별로 고르면 된다.
- `overlapReason`이 `'{{count}} countries in common'`이라 count=1일 때 "1 countries".
  프로젝트 전반에 `_one`/`_other` 복수형이 도입돼 있지 않다 — 로케일 전반 작업으로 분리.

## 개인정보 — 방침 문서 대조 필요

이번에 노출 해상도가 **국가 → 도시**로 한 단계 내려갔다(`shared_cities`).
계산에 쓰이는 것은 `visibility <> 'private'` 기록, 즉 **메이트 전용 기록**인데
추천 대상은 정의상 **아직 메이트가 아닌 사람**이다.

수집 항목·목적은 `docs/privacy-policy.md` 제1조 3)·4)에 이미 명시돼 있어 개정이 필수는 아니다.
다만 제9조("메이트 전용 기록 접근을 서버단에서 차단")와 긴장 관계가 생겼다.
표시되는 것은 **내 데이터와의 교집합**이라 내가 이미 가 본 도시만 보이지만,
일반 이용자 인식으로는 구분이 어렵다.

최소 조치로 제1조 4)에 한 줄 추가를 권한다:

> 추천 메이트 산출 시 상대와 공통으로 겹치는 범위(국가·도시·키워드)에 한해 겹침 사실이
> 표시되며, 기록 본문·사진·날짜는 공개되지 않습니다.

명세 §7의 "새로 노출되는 정보가 없다"는 서술은 사실과 다르다(도시·키워드가 신규).
